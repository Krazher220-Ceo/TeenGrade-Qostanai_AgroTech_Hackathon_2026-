Хронология работы над веткой `feature/post-hackathon`, начиная с состояния, которое было отправлено на хакатон (`63e8e2a`, «Merge pull request #1 from Krazher220-Ceo/feature/cheatsheet-improvements»). Задача этого этапа — устранить разрыв между тем, что обещал питч, и тем, что реально делает код, и довести документацию до состояния, где каждая цифра подтверждена файлом.

## 3. HITL-дообучение и реестр многолетников (`b5c975f` … `9887c74`)

- `case1/ml/hitl_export.py` — экспорт подтверждённых решений агронома из серверного реестра (`verified_actions.json` + `all_fields_detections.csv`) в manifest CSV, читаемый `WeedMultiTaskDataset`. Нерешительные/отменённые записи исключаются, решения «культура» идут в фоновый класс `crop_wheat`, сплит на train/val/test — по кадру (не по объекту), чтобы один и тот же снимок не «утёк» между train и test.
- `case1/ml/finetune_hitl.py` — короткое дообучение от текущего чекпойнта на смеси исходного датасета и HITL-примеров; кандидат оценивается против baseline на отложенной выборке; рабочий чекпойнт подменяется только вручную и только если кандидат не хуже (`decide_promotion`).
- `GET /api/v1/hitl/stats`, `python case1_main.py hitl-export` — видимость накопленных решений.
- `case1/data/perennial_registry.py` — SQLite-реестр многолетников по полю/сезону/кадру, список видов вынесен в `PERENNIAL_SPECIES_MARKERS/CODES` в `case1/fleet/agronomy_rules.py` (раньше дублировался). Заполнен одним реальным сезоном (`case1/output/all_fields_report.json`) и одним явно помеченным `seed_demo_season` синтетическим сезоном для демонстрации сравнения.
- `GET /api/v1/perennials`, `GET /api/v1/perennials/compare`, вкладка дашборда «Многолетники по сезонам».
- По коммиту добавлено 51 тест; итог на тот момент — 107 passed из известного набора (7 ранее существовавших падений из-за отсутствующих весов/датасетов, не связанных с этим изменением).

## 4. Единый порог ручной проверки (`c3272c4`)

Порог уверенности классификатора вида был захардкожен тремя разными значениями в разных местах: 0.65 в `multitask_model.py`, 0.60 по умолчанию в `case1_main.py --species-conf`, 0.65 в `viewer_pipeline.py`, 0.60 в слайдере дашборда. Питч обещал единый порог 0.75. Добавлен `case1/configs/loader.py::get_species_confidence_threshold()`, читающий `review.species_confidence_threshold` из `case1/configs/settings.yaml`; все потребители (классификатор, CLI-флаг, viewer_pipeline, дашборд, текст `/model-info`) теперь берут значение из одной функции.

## 5. 26-классовый классификатор по умолчанию (`f31ccec`, `d17e776`, `efe9007`)

- `f31ccec` — питч утверждал «26 видов, 3 фазы, 98.4%/98.7%», но все потребители (`server/app.py`, `case1_main.py`, дашборд, `viewer_pipeline.py`) грузили `multitask_weeds_best.pt`, который на деле был старым 4-видовым/2-фазным чекпойнтом. Настоящий 26/3-чекпойнт (проверено по форме `species_head.4.weight` → (26, 256), `stage_head.4.weight` → (3, 256)) лежал неиспользуемым в `case1/models/server_2026-09-17/`. Он сделан чекпойнтом по умолчанию; старый 4-классовый сохранён как `case1/models/multitask_weeds_legacy_4cls.pt` (не удалён, доступен явно). `case1/output/classifier_training_metrics.json` обновлён метриками актуального чекпойнта. Добавлен `case1/tests/test_default_model.py`, закрепляющий 26/3 и порог 0.75 как контракт.
- `d17e776` — баг: для объекта с нераспознанным видом (`is_unknown=True`) движок агрономических правил всё равно смотрел фазу по умолчанию (`cotyledon_to_2_leaves`) и возвращал статус `optimal` («оптимальное окно для обработки») — то есть неопознанный объект мог показываться как готовый к точной дозировке. Исправлено: при `is_unknown=True` фаза сразу помечается `undetermined` («Фаза не определена»), без похода в `agronomy_rules.json`. Добавлен регрессионный тест.

## 6. Геопривязка, зоны обработки, ISO-XML Grid Type 2 (`0ee706b`, работа велась в `wt/geo-isoxml`)

Задача и итоговый отчёт исполнителя — `docs/antigravity_task_geo.md`. Раньше все сорняки одного кадра получали одну и ту же GPS-точку кадра, зон вокруг очагов не было, `TASKDATA.XML` собирался вручную в дашборде и не соответствовал ISO 11783-10.

- `case1/geo/georef.py` — перевод пикселя бокса в WGS84-координату по EXIF (высота, фокусное расстояние, yaw), с откатом на координату кадра (`geo_quality="frame_only"`) при неполном EXIF.
- `case1/geo/zones.py` — буферные зоны вокруг очагов (0.5 м / 1.5 м для однолетних/многолетних, `case1/configs/agronomy_rules.json → treatment_zones`), объединение пересекающихся зон через `geopandas`/`shapely`, исключение культуры и объектов на ручной проверке.
- `case1/geo/isoxml.py` — экспорт ISO 11783-10 TASKDATA Version 4 (`CTR/FRM/PFD/PDT/TSK/TZN`) с растровой сеткой Grid Type 2 (`GRD00001.bin`).
- Новая CLI-команда `python case1_main.py prescribe` — из отчёта детекций собирает `points.geojson`, `zones.geojson`, Shapefile (`zones.shp/.dbf/.prj/.shx/.cpg`), `TASKDATA/` (XML + бинарная сетка + zip) и `summary.json`.
- Вкладка дашборда VRA переведена на вызов нового экспортёра вместо ручной сборки XML, добавлена отрисовка зон на карте.
- `scripts/verify_prescription_and_taskdata.py` и `case1/tests/test_prescription_adversarial.py` обновлены под формат с зонами и сеткой.
- Прогон на 5 реальных кадрах из `Dataset 1 кейс/` сохранён в `case1/output/prescription_v2/` (3 зоны, 21.18 м², 0.53 л по `summary.json`); точки внутри кадра больше не совпадают.
- Официальная XSD-валидация AEF не пройдена (недоступна без регистрации) — вместо неё структурные проверки в тестах; это явно отмечено как открытый пункт, а не как «принимается терминалом».
